# 비동기 작업 부하 테스트는 접수 이후까지 측정한다

> 2026-10-15

## 배운 것

작업을 접수하고 HTTP 202를 반환하는 API는 접수 응답만 빨라도 사용자 결과가 늦을 수 있다. 부하 시험에서는 실제 사용자 흐름의 끝점을 먼저 정해야 한다.

```text
작업 접수 → 상태 polling → 완료 → 저장된 결과 조회 → 필요한 후속 화면 데이터 조회
```

이번 시험은 추천 접수부터 저장 일정과 첫 코스 목록 조회까지 측정하고, 목록을 다시 읽어 내용도 대조했다. 초당 3건은 이 전체 흐름이 매초 세 번 시작된다는 뜻이다. polling·결과 조회를 포함한 HTTP 호출 수나 동접자 수와 같지 않다.

| 관측 | 확인할 내용 |
| --- | --- |
| 접수·완료·저장 조회 | 접수된 작업이 실제 결과까지 제공되는가 |
| dropped_iterations | 계획한 흐름 중 시작하지 못한 것이 있는가 |
| PENDING/RUNNING·작업 해소 | 유입 중 대기가 쌓이고 종료 후에도 남는가 |
| 구간별 p95 | 특정 시점의 지연이 전체 통계에 가려지는가 |
| 단계별 시간·CPU·DB | 어디서 계산하거나 기다리는가 |
| 결과 내용·롤백 | 성능 변경이 결과나 저장 일관성을 깨뜨리는가 |

k6의 arrival-rate 실행에서는 사용 가능한 VU가 없으면 예정된 iteration을 시작하지 못할 수 있다. `dropped_iterations`는 서버가 반환한 HTTP 오류와 구분해 기록한다. [k6 문서](https://grafana.com/docs/k6/latest/using-k6/scenarios/concepts/dropped-iterations/).

## 막혔던 것 / 해결

### 서버 시간 지표에서 저장 비용이 빠졌다

기존 코드는 처리시간과 완료 시각을 정한 뒤 결과 저장을 호출했다. 해당 지표를 DB 커밋까지 끝난 시간으로 읽으면 저장 비용을 놓친다. 진단에서는 작업 대기·계산·후보 저장을 나누고 클라이언트는 저장 결과 조회까지 측정했다. 정식 완료 지표의 경계 변경은 별도 미완료 작업으로 남겼다.

상위 작업 시간에는 하위 저장 시간이 포함될 수 있다. 중첩된 구간을 더해 전체 시간을 계산하지 않는다. 상세 SQL 계측 자체도 비용을 만들 수 있어, 배치 변경은 상세 계측을 끈 동일 조건 비교로 다시 확인했다.

### 전체 p95만 보면 장기 구간 실패를 놓쳤다

2026-10-11 로컬 시험의 조건은 백엔드 2 CPU/4 GiB, DB 1 CPU/2 GiB, Python worker 두 개, 탐색 예산 100ms, 후보 배치 저장이었다. 대표 흐름 40개 예열과 준비 부하 후 3.5건/초를 10분 측정했다. 사전 기준은 각 5분 구간의 p95가 2초 이내였다.

- 실행된 2,101건은 모두 완료했고 미실행은 0건이었다.
- 전체 p95는 1.242초였다.
- 전반 5분 p95는 1.094초, 후반은 2.740초였다.

전체 p95만 보면 빨라 보이지만 구간 기준에서는 실패다. 이 판정을 보존하고 느린 시점의 DB·commit·실행기 대기를 후속 조사 대상으로 남겼다. 초당 3.5건을 안정적인 최대 처리량으로 발표하지 않는다.

### health UP이 기존 작업의 복구를 뜻하지 않았다

작업 처리 중 백엔드를 종료하고 재시작하자 새 요청은 성공했지만 기존 네 작업은 관측 30초 동안 RUNNING에 남았다. 같은 요청 키를 재사용해도 실행이 재개되지 않았다. DB의 작업 상태와 메모리 실행기의 수명이 달랐다.

작업 소유권·기한을 관리해 중단 작업을 재시도 가능한 실패로 종료하거나, 저장한 입력을 안전하게 재개하는 설계가 필요하다. 이것은 발견한 문제와 수정안이며 아직 구현 완료한 성과가 아니다.

위 결과는 한 노드의 로컬 검증이다. 운영 최대 동접, 실제 외부 API 장애, 다중 서버 복구와 추천 만족도를 입증하지 않는다.
