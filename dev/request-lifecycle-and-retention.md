# 요청값은 얼마나 유지되는가

> 2026-09-22

## 배운 것

"요청으로 들어온 값은 얼마나 유지되나요?"라는 질문에는 하나의 숫자로 답할 수 없다. 무엇의 수명을 묻는지 먼저 나눠야 한다.

| 대상 | 수명이 결정되는 기준 |
| --- | --- |
| 요청 파라미터·DTO | 보통 HTTP 요청을 처리하는 동안 사용하고, 저장하지 않으면 응답 뒤에는 남지 않는다 |
| DB 데이터 | 트랜잭션이 커밋된 뒤 삭제·보존 정책에 따라 남는다 |
| 인증 토큰 | 발급할 때 정한 만료시간과 갱신 정책을 따른다 |
| 캐시 | TTL과 무효화 정책을 따른다 |
| 열린 연결 | 서버·프록시·클라이언트의 timeout까지 유지된다 |
| 배치 작업 | cron이나 fixed delay에 따라 실행된다 |

`timeout`, `TTL`, `interval`은 서로 다른 값이다.

- `timeout`: 얼마나 기다리다 포기할 것인가
- `TTL`: 데이터를 언제까지 유효하다고 볼 것인가
- `interval`·`cron`: 작업을 얼마나 자주 실행할 것인가

예를 들어 SSE 연결 timeout이 5분이라고 해서 DB에 저장된 작업 결과가 5분 뒤 삭제되는 것은 아니다. DB healthcheck가 5초마다 실행된다고 해서 애플리케이션이 업무 데이터를 5초마다 조회하는 것도 아니다.

일반적인 DB 요청은 다음처럼 동작한다.

```text
HTTP 요청
  -> Controller
  -> Service
  -> Connection Pool에서 연결을 빌림
  -> Repository가 SQL 실행
  -> commit 또는 rollback
  -> 연결을 Pool에 반납
  -> HTTP 응답
```

Connection Pool은 DB 연결을 재사용한다. 애플리케이션과 DB가 일정한 주기로만 통신하도록 만드는 기능이 아니다. 실제 쿼리 시점은 요청 처리, 스케줄 작업 또는 별도 비동기 작업이 결정한다.

## 막혔던 것 / 해결

처음에는 "몇 초 동안 유지됩니다"처럼 하나의 설정값을 찾으려고 했다. 하지만 요청 객체, DB 행, 토큰, 캐시, 스트리밍 연결은 소유자와 종료 조건이 모두 달랐다.

이후에는 다음 순서로 확인한다.

1. 어떤 값을 말하는지 구분한다.
2. 그 값을 메모리, DB, 캐시 중 어디에 두는지 찾는다.
3. 저장·갱신·삭제를 담당하는 코드를 찾는다.
4. timeout, TTL, 배치 주기를 따로 확인한다.
5. 응답이 끝난 뒤에도 남는 값과 사라지는 값을 구분한다.

이 구분을 먼저 하면 "요청이 얼마나 유지되나요?"라는 질문을 설정값 암기가 아니라 데이터의 생명주기로 설명할 수 있다.

## 참고

- 요청 흐름은 `Controller -> Service -> Repository` 이름만 외우지 않고, 저장 위치와 트랜잭션 경계까지 따라간다.
- 설정 파일의 숫자는 이름만 보지 말고 timeout, TTL, interval 중 무엇인지 확인한다.
- 로컬 테스트 결과만으로 운영 프록시나 외부 서비스의 실제 timeout을 확정하지 않는다.
