# 경로 계산용 Python 프로세스를 재사용하기

> 2026-10-15

## 배운 것

Python worker는 요청을 받아 계산하는 Python 프로세스다. 새 라이브러리의 이름이 아니다. worker pool은 여러 프로세스를 준비해 두고 계산을 나눠 맡기는 구조다.

Spring에서 Python 경로 계산기를 호출할 때 다음 두 방식은 계산 함수가 같아도 비용이 다르다.

```text
매번 실행: 요청 → Python 시작 → OR-Tools import → 계산 → 종료
재사용:    Python 시작·import 한 번 → 입력 대기 → 계산·응답 → 입력 대기
```

프로세스 재사용에는 대기 중 메모리를 유지하는 비용이 있다. 대신 요청마다 반복하던 라이브러리 적재를 줄일 수 있다. 입력을 blocking read로 기다리면 대기 중에 계산을 계속 돌릴 필요는 없다.

이 변경 자체가 호출을 비동기로 만드는 것은 아니다. 이번 구현에서도 Java의 계산 호출은 결과를 기다렸다. 이미 비동기로 실행되는 작업 안에서 Python 프로세스의 수명을 바꾼 것이다.

## 막혔던 것 / 해결

단일 요청은 빨랐지만 지속 유입에서 작업 대기가 커졌다. 단계별 시간을 확인하니 탐색 시간은 약 100ms를 유지하는데 Python 전체 실행과 import 시간이 늘었다. 기본 일정과 대안을 계산하면서 같은 초기화를 반복하고 있었다.

로컬 구현에서는 계산 함수를 유지하고 worker 두 개를 재사용했다. 동시에 실행되는 계산과 대기도 제한했다.

- worker 하나에는 한 번에 요청 하나만 전달한다.
- 요청 ID로 응답을 대조하고 출력 크기를 제한한다.
- worker를 기다리는 시간부터 응답까지 하나의 timeout으로 관리한다.
- timeout·잘못된 응답·비정상 종료가 발생하면 해당 worker를 폐기하고 교체한다.
- stdout은 응답 전용으로 사용하고 stderr도 처리해 파이프가 막히지 않게 한다.
- 부모 서비스가 종료되면 자식 프로세스도 정리한다.

일반적으로 stdout/stderr를 PIPE로 연결한 뒤 읽지 않으면 출력 버퍼 때문에 자식 프로세스가 멈출 수 있다. [Python subprocess 문서](https://docs.python.org/3/library/subprocess.html#subprocess.Popen.wait).

### 로컬 비교 결과

측정일은 2026-10-08이다. 백엔드 2 CPU/4 GiB, PostgreSQL 1 CPU/2 GiB, 탐색 예산 100ms를 유지하고 동일 이미지에서 pool만 off/on으로 비교했다. 아래는 초당 새 작업 흐름 3건·60초 구간이며 완료 polling과 저장 결과·첫 코스 조회까지 포함한다.

| 항목 | 매번 실행 | worker 재사용 |
| --- | ---: | ---: |
| 첫 코스 조회까지 p95 | 20.429초 | 1.110초 |
| 시작하지 못한 흐름 | 26건 | 0건 |
| 관측 PENDING 최대 | 32건 | 0건 |

반복 초기화 제거와 동시 실행 제한을 함께 적용한 효과다. 계산 함수 하나가 20초에서 1초가 됐다는 뜻은 아니다. 작업이 밀리며 생긴 대기가 크게 줄었다. 같은 사용자·여행 다섯 쌍의 결과 보존과 worker 강제 종료 후 교체도 확인했다.

worker 하나의 RSS는 약 43MB였다. 후속 지속 시험에서는 유휴 207초 동안 CPU tick 증가가 0으로 관측됐다. 이 수치로 장기 메모리 누수나 모든 환경의 자원 사용을 보장하지 않는다.

로컬 실험 구현이며 운영에 반영한 성과가 아니다. 정식 적용에는 서비스 lifecycle, 제한된 오류 로그, 실제 입력의 결과 보존과 장기 자원 관측이 필요하다.
